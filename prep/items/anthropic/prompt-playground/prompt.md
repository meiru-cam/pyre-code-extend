Design a browser-based playground where developers at a customer organization write, run and iterate on prompts for a hosted language model, then save, share and test the versions they keep. A *prompt* is the named object a user creates. It holds a system prompt (plain text), an ordered list of messages (`{role, content}` with `role` one of `user` or `assistant`; the list must start with a `user` message and strictly alternate roles, the same shape the model API itself requires), a set of *variables* — placeholders of the form `{{name}}` that may appear inside the system prompt or any message's content, each with an optional default value — and a set of model parameters: `model` (one of a fixed catalog of model identifiers), `temperature` (a float from 0 to 1 inclusive), `max_tokens` (a positive integer, capped at 8,192) and up to 4 `stop_sequences` (strings). Variable substitution is a plain text replace of every `{{name}}` occurrence with its bound value; a bound value that itself contains `{{` or `}}` is inserted verbatim and never re-substituted. A prompt's current, editable content is its *draft*. Saving the draft under a label creates a *version*: an immutable snapshot of the draft's content at that moment. A *run* is one invocation of the model against a specific version, or against the current draft, with a value supplied for every variable that occurs in its text and carries no default — streamed back to the browser token by token and recorded once it finishes, fails, or is cancelled; a run request missing a value for such a variable is rejected outright, naming every variable it is missing, and never reaches the model API. A *test case* is a named set of variable values, saved against a prompt, used to re-run every version of that prompt against the same inputs. A *share* grants another user, an entire organization, or anyone holding a link, a chosen permission level on a prompt: at least the ability to view and run it, and optionally to edit its draft and save new versions.

The model is reached through an existing HTTP endpoint, `POST /v1/messages`, with a JSON body `{model, system, messages, temperature, max_tokens, stop_sequences, stream}`. With `stream: true` it returns a chunked response carrying a sequence of `{type: "delta", text}` events with newly generated text, followed by one `{type: "stop", reason, input_tokens, output_tokens}` event, where `reason` is `"end_turn"`, `"max_tokens"`, or `"stop_sequence"`. Before streaming starts the endpoint may instead refuse with HTTP `429` (rate-limited) or `503` (overloaded); once streaming has started, a failure ends the event sequence with `{type: "error", message}` in place of the `stop` event. The endpoint bills per input and output token and stops generating as soon as the caller closes the connection.

The editor page shows one prompt at a time: a system-prompt box, the message list, a variables panel that prefills every `{{name}}` with its default and lets the current run override any of them, and a parameters panel for `model`, `temperature`, `max_tokens` and `stop_sequences`. A Run button streams the model's reply into a read-only panel beside the editor. A Compare action opens several such run panels side by side, each independently configured (a different saved version, model, or parameter set, all run against the same variable values). A sidebar lists the prompts the signed-in user can reach; opening one loads its current draft and a history list of its saved versions. A Save action labels the current draft as a new version. A Share action grants a teammate, the whole organization, or (by link) anyone else a permission level on the prompt. A Test cases panel lists a prompt's saved input sets and can run a chosen subset, or all of them, against one version at once.

Scale for this design:

- 250,000 registered developer accounts across customer organizations, of whom 15,000 are active on a given day.
- An active user runs a prompt about 15 times a day while iterating, and turns about 2 of those iterations into a saved, named version.
- A registered user has about 12 prompts on average, and a prompt accumulates about 6 saved versions over its lifetime.
- Usage concentrates in a 12-hour window common to most customers' working hours, which carries about 72% of a day's runs; assume a 2x burst factor over that window's average rate for the single busiest minute.
- The model streams output at about 50 tokens/second, and a run's output averages 400 tokens.
- A prompt's serialized content (system prompt, messages, variables and parameters together) averages 1.5 KB; the largest the system accepts is 8 MiB.

In scope: the create, run, iterate, save, share and evaluate flow above; the schema and REST API behind it; the versioning and concurrency-control model for two teammates editing the same prompt at once; the permissions model for sharing, at both the organization and the individual level, including how a share is revoked and restored; how a prompt whose serialized content is very large is accepted, stored and kept responsive to edit; and per-user and per-organization cost and rate control, plus what is recorded for audit. Out of scope: the identity service that authenticates a request and attaches a verified user id and organization id to it (assume both already arrive on every request that reaches the web server); the model API's own implementation, batching or serving infrastructure; building an automated scoring pipeline over test-case outputs (a test case here is a saved input to re-run, not a grader — an evaluation pipeline is a follow-up); and real-time, character-by-character co-editing of one draft by two people at once — only what happens when two independent saves race is in scope.

Produce:

- Core user flows: create a prompt, run it, iterate and compare runs side by side, save a version, share it, and build and re-run a set of test cases.
- A data model — prompts, versions, runs, test cases, and the tables behind sharing — with primary keys, foreign keys and the indexes each flow above needs, plus the core REST API's request and response shapes.
- An architecture diagram covering the browser, the web server, the relational database and the model API, showing where large content lives, and a walk-through of one streamed run along it.
- Deep dives into: (a) streaming a run and running several side by side; (b) the versioning model — the mutable draft, immutable versions, concurrency control between two teammates saving at once, and what happens when a version still referenced elsewhere is deleted; (c) the sharing and permissions model, at the organization and the individual level, and revocation; (d) very large prompts — where the content lives and how the client stays responsive — plus per-user and per-organization cost and rate control, and what is logged.
